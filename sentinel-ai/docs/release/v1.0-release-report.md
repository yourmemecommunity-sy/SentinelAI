## 8. Defects found and fixed at this stage

1. **Token vault failed closed under a burst of legitimate traffic in dev/test.** redis-py 8 caps its default asyncio pool at
   100 connections and *raises* when it is full; fakeredis uses that pool, so 200 concurrent tokenizations failed with
   `VaultUnavailable` (seen in the `act` token-vault job). Production already used a bounded *blocking* pool; the `memory`
   backend and the test fixture now use the same pool (`app/factory.build_fake_client`). New regression test (300-way burst).
   Mutation-checked, and 8/8 passes under 2× CPU oversubscription where the old setup failed about 1 run in 5.
2. **Chaos checker classified chats by the wrong outage window.** The window started when `docker compose kill` was *issued*
   and ignored request duration, so a chat that obtained its tokens just before the kill, or reached the restarted vault,
   counted as "served during the outage". One run reported 2 such chats. The window now starts once the kill has returned and
   only counts chats that run entirely inside it; boundary chats are listed. A code review found no fail-open path (the engine
   builds a vault client per request and turns every vault error into `FailClosed("vault_unavailable")`), and the rerun gave
   10/10 fail-closed. The raw data from the failing run was lost with its temporary directory, so the explanation is
   **probable, not proven**. The leak invariant held in both runs.
3. mypy findings (§2). Earlier in this stage: synthetic datasets defanged for push protection; control characters and lone
   surrogates rejected in display names (found by fuzzing).

## 9. Accepted risks

* Unfixed Debian base-image CVEs: Python images 44 HIGH each; document scanner 72 HIGH + 1 CRITICAL in libxml2
  (CVE-2026-6653), which Tesseract links. The scanner runs non-root, read-only, on an internal network with no egress.
* The evaluation corpus is self-authored. 100% on it is necessary but not sufficient.
* Performance is a single-VM baseline (~145–185 req/s), not capacity planning.

## 10. Open issue: intermittent SDK test failure on the Windows host

Out of about 78 full runs of the JavaScript SDK suite on the Windows host, 5 failed. Each time one test's request to its
**local** stand-in server was rejected ("cannot reach the SentinelAI gateway"), in a different test each time, and one of the 5
happened under deliberate CPU overload. The final host regression hit it once (60/61). Linux: 0 failing runs in 30, and the
`act` gateway job, which runs this suite, passed. Refuted causes: keep-alive socket reuse on a recycled port (0/200 in a
direct reproduction) and port sharing with uvicorn (Windows refuses the bind). **Root cause not determined.** Every
occurrence surfaced as a fail-closed `SentinelUnavailableError`, never a wrong success, so there is no evidence of a product
defect. It is recorded as a test-reliability issue, **not** as a pass.

## 11. What this report does not claim

Production readiness; any real call to Gemini, OpenAI or Anthropic; CI on GitHub-hosted runners; managed-cloud,
multi-node or long-duration operation; external red-team coverage.
